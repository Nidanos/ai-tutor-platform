2.2 Identified deficiencies
1. Completion is measured instead of capability. Every platform records what
has been watched or ticked. None records what the learner can independently
produce. A 100% completion figure is compatible with zero ability to write the code
unaided.
2. Recognition is trained; recall is not. Watching an instructor write code is a
recognition task. Producing code from a specification is a recall and construction
task. These are distinct cognitive operations and competence in the first does not
transfer to the second. The learner experiences the feeling of understanding
throughout, and discovers its absence only when asked to build something.
3. Curricula are linear; learners are not. A course is a fixed sequence authored for
a median learner who does not exist. Time spent on already-known material is

time removed from unknown material. The author's own diagnostic scored 10/11
on reading code and 0/4 on writing it — a profile no linear course can respond to.
4. No system maintains a model of what the learner knows. Absent a
representation of current state, no defensible next step can be selected. The
learner selects the next video, which is not the same as selecting the next thing to
learn.
5. Generative AI has made the problem materially worse. An AI assistant asked
for an explanation supplies one; asked for code, supplies code. The learner's
productivity rises and their capability does not, because effortful retrieval — the
struggle — is the mechanism by which memory is formed. Existing AI tutoring
products optimise for perceived helpfulness in each individual interaction, which is
precisely the wrong objective function for learning.
6. Nothing survives disuse. Material learned in week one, never revisited, is
substantially lost by week five. No mainstream product schedules revision against
a model of individual forgetting.
7. The blank page terminates sessions. For learners with attention-regulation
difficulties in particular, an unstructured task with no obvious first action does not
produce slow progress — it produces abandonment. Session abandonment is the
only true failure mode, and no existing product designs against it.

2.3 Cost of the existing system
For the individual learner, the cost is measured in months. Six weeks of full-time study
producing recognition without production capability is six weeks that must be
substantially repeated. Where the learner is preparing for employment, this delay
carries direct financial cost in deferred salary.
At market scale, the cost is visible in completion statistics. Massive open online courses
are widely reported to exhibit single-digit completion rates, and the proportion of
completers who can subsequently work unaided is not measured by any provider —
because no provider measures capability at all. The paid ed-tech market therefore sells
a product whose effectiveness is, by construction, unmeasured.

Gap identified: no existing system maintains a separate model of reading and
writing ability per skill, updates it only from executed evidence, selects the next
step from a prerequisite graph rather than a fixed sequence, and deliberately
withdraws its own assistance on a schedule. Each of these mechanisms is

individually established in the learning-sciences literature. None of them is
commercially implemented together, because doing so reduces engagement metrics —
which is a business-model constraint, not a technical one, and is therefore an opening.

3. Description of the Proposed System
The proposed system is a web-based, online application accessible through a
standard browser with no installation required, comprising a learner-facing session
interface, an embedded code editor, a sandboxed execution service, and a set of
backend services maintaining a per-learner model of skill mastery.

3.1 Governing design principle
The system optimises for the learner's independent capability over time,
not for the learner's satisfaction within any individual interaction.
Every design decision in this document derives from that statement. Where the two
objectives conflict — and they frequently do — independent capability takes
precedence. The clearest expression of this is that the system will refuse to supply
solution code, and treats every occasion on which it was forced to supply an answer as
a recorded system failure rather than a service rendered.

3.2 Positioning and scope decisions
Single domain in version one. The system implements one skill graph — JavaScript
through to React — comprising approximately sixty nodes, hand-authored. Breadth is
deferred deliberately; a shallow graph across many domains would not demonstrate the
mechanism and would not be defensible.
Text, code and exercises only. No video content. Video is the medium whose failure
mode this project exists to address, and reintroducing it would place the product in a
category with many well-funded incumbents.
The learner is the unit of value, not the content. The system's asset is the
accumulated model of what each learner can do and the evidence supporting it. Course
content is a commodity; a calibrated learner model is not.

Human-authored curriculum, machine-generated exercises. The skill graph and
its prerequisite structure are authored by hand because they are the spine of the
system and must be correct. Individual exercises are generated per learner and per
difficulty rung, and are executed against their own tests before ever being served.

3.3 Distinguishing characteristics
Three mechanisms differentiate this system, and each is enforced structurally in code
rather than stated as an intention.
1. Separate reading and writing mastery per skill. Every skill node carries two
independent scores for each learner: the ability to comprehend code that uses the skill,
and the ability to produce it unaided. These diverge substantially in practice — the
author's own measured profile was 10/11 and 0/4 respectively — and a single blended
score would have produced an entirely incorrect next-step recommendation. This split
is the central design decision of the system.
2. Evidence-only mastery updates. A mastery score moves when the learner
submits code that is executed and passes its tests, when a prediction about program
behaviour is correct, or when an exercise is solved. It never moves because content
was marked as read, watched or completed. Evidence is weighted by exercise difficulty,
by the number of hints consumed, and by time taken.
3. Scheduled withdrawal of scaffolding. Assistance reduces over time on a planned
schedule rather than in reaction to learner requests. Early sessions provide worked
examples; intermediate sessions provide partially completed files; later sessions
provide a specification and an empty file. The fade is a configured property of the
learner's plan, not an emergent behaviour.

3.4 The learner model
The learner model is the substantive engineering contribution of the project and the
component on which every other module depends.
Skill representation. Skills are stored as a directed acyclic graph with explicit
prerequisite relationships, rather than as an ordered list. Selecting a next step becomes
a query over this graph.

Mastery representation. For each learner and each skill, the system stores a reading
score, a writing score, the timestamp of the most recent supporting evidence, attempt
and success counts, and a per-skill decay constant.
Mastery decay. Effective mastery is computed as the stored score attenuated
exponentially by time elapsed since the last supporting evidence, with the decay
constant varying by skill type — syntactic knowledge decays rapidly, conceptual
knowledge slowly. When effective mastery falls below a threshold, the skill re-enters
the review queue. This addresses deficiency 6 in §2.2 as a property of the data model
rather than as a feature bolted alongside it.
Next-step selection. Selection is deterministic and computed by the system, not
delegated to a language model. Candidate skills are those whose prerequisites are
sufficiently mastered, together with those due for review. Candidates are scored on
prerequisite readiness, relevance to the learner's stated goal, urgency derived from
decay, and recency of coverage. The highest-scoring candidate is chosen and the
exercise difficulty rung is set from the writing score. A language model then generates
the content of that step. Preserving this boundary — the system decides which step,
the model produces what is in it — is what makes the system explainable and
inexpensive to operate.

3.6 The Socratic response engine
The refusal to supply solutions is enforced by three independent mechanisms, because
a constraint expressed only in a model prompt is not a constraint.
Server-side hint ladder. Assistance is emitted at escalating levels of specificity —
indicating the relevant concept, then the relevant location, then naming the mechanism,
then presenting an analogous worked example, and only finally the answer itself. The
currently permitted level is held server-side and advances only on explicit learner
request. The language model receives one level at a time and never the full ladder.
Output filtering. Generated responses are inspected before transmission for solutionshaped code matching the current exercise target, and are blocked if found.
Bottoming-out as telemetry. Every occasion on which the ladder reaches its final
level is recorded as an indication that the step presented was too large, and is fed back
into difficulty calibration.

6. Methodology
6.1 SDLC Model to be Used
Incremental and iterative development, organised into defined phases, with a
preliminary manual validation phase preceding any implementation.

6.2 Justification for the Selection of the
Model
The central hypothesis of this project — that adaptive laddered exercises with
scheduled scaffolding withdrawal produce better retained capability than linear course
consumption — is testable without software. Phase 0 therefore operates the entire loop
manually, on paper, with a real learner, before any implementation begins.

This ordering is deliberate and is defended as follows: if the hypothesis fails on paper it
will fail in software, and the failure will have cost two weeks rather than several months.
Building the machinery first would represent significant engineering investment in an
unvalidated premise.
Subsequent phases are incremental because the learner model requires empirical
calibration. Each increment produces a working system whose predictions can be
compared against observed learner performance, and the calibration improves with
each cycle. A waterfall model would defer all such feedback to a single point after
implementation, which is unsuitable for a system whose correctness is statistical rather
than functional.

6.3 Testing Approach
Unit testing of the mastery-update and decay mathematics against constructed
evidence sequences; integration testing of the generation-and-validation pipeline
including deliberate injection of invalid generated exercises; security testing of the
sandbox against resource exhaustion, network egress and filesystem escape; system
testing of complete learner journeys; and calibration testing, in which predicted
mastery is compared against outcomes on held-out challenge exercises. The
calibration error rate is treated as a first-class quality metric of the system rather than
as a diagnostic.

7. Commercial Viability
The system is developed as a product rather than as an academic exercise. This
section records the commercial reasoning.

7.1 The market problem being sold against
Purchasers of technical training — individuals, employers funding upskilling, and
educational institutions — currently have no means of verifying that training produced
capability. Providers report completion; buyers require competence. This system
measures capability directly and produces evidence for it, which is a materially different
product from the one presently on sale.

7.2 Revenue model
Individual subscription. Monthly access for self-directed learners. This is the entry
route and the source of early calibration data.

Institutional licensing. Bootcamps, training providers and colleges purchase seats.
The buyer's incentive here aligns with the system's design in a way that the consumer
market's does not: an institution accountable for graduate outcomes benefits from a
product that measures capability honestly, whereas a consumer may prefer a product
that feels comfortable. This is the stronger commercial route and the design does not
have to be compromised to serve it.
Employer-facing verified capability profiles. A longer-term route in which the
mastery model, backed by executed evidence, functions as a credential. This is
credible precisely because mastery is only ever updated from executed evidence, and
is not available to any provider that records completion.

7.3 Defensibility
The prompts are not defensible; the curriculum graph is moderately so; the
accumulated attempt data is strongly so. Records of which exercise sequences
produced measurable capability gains, across many learners, constitute a dataset that
improves the system's difficulty calibration and cannot be obtained without having
operated the system. A well-funded competitor can replicate the interface in weeks and
cannot replicate that dataset at all.

7.4 The structural advantage
Incumbent products are constrained by engagement metrics. A product measured on
time-in-application cannot adopt a design whose explicit goal is that the user finishes
sooner and returns less. This system treats time-in-application as an anti-metric —
a reduction in it, at constant capability gain, is a product improvement. That position is
available only to an entrant, and it is the commercial reason this project is viable
despite the presence of far larger competitors.

7.5 Validation gate
The project carries an explicit commercial validation gate: a learner who is not the
author must complete a multi-session project using the system. Until that gate is
passed, the system is a tool built for one person, and this is recorded as a risk rather
than obscured.

8. Future Scope
The complete web application is delivered within the current semester. The following
extend the system beyond that delivery.
1. Additional skill domains — Node.js, PostgreSQL, system design — added
without modification to the engine, demonstrating that the architecture is domainindependent.
2. Spoken explanation assessment. The learner explains a concept aloud and is
assessed on the explanation. Explanation quality is among the strongest available
indicators of genuine understanding.
3. Editor integration. Observation of the learner within their own development
environment, with intervention only at points of genuine difficulty.
4. Community-authored skill graphs, enabling coverage to grow beyond what the
team can author directly.
5. Cohort mode — shared paths with light accountability, for institutional
deployments.
6. Effectiveness dataset exploitation — systematic analysis of which exercise
sequences produce measurable capability gains, feeding back into generation.
7. Portable learner model, allowing a mastery profile to be exported and
recognised across tools.
